# Prepare Puente Resources

Create a bilingual CSV that passes the current Puente ATX importer. Preserve provenance, avoid invented facts, and leave production unchanged.

## Workflow

1. Locate the Puente ATX project. Prefer the current workspace; otherwise find a project containing `src/data/csvImport.js` and `package.json` with the Puente ATX application.
2. Read these live project files completely before transforming data:
   - `src/data/csvImport.js`
   - `src/data/categories.js`
   - `src/data/serviceAreaNormalization.js`
   - `src/data/resourceValidation.js`
   - `src/config/serviceAreas.js`
3. Treat the live `CSV_IMPORT_HEADERS`, category definitions, normalization rules, and validation logic as authoritative. Never rely solely on a copied template or remembered schema.
4. Extract the source document without changing it. Keep an immutable extracted copy and derive every later pass from that copy, not from summaries, titles, categories, or translations generated by an earlier pass. Make transformations idempotent: running the same enrichment twice must not progressively change classifications or duplicate notes. Support CSV, XLSX, DOCX, PDF, and paired bilingual documents. If text extraction is unreliable or OCR would materially affect accuracy, stop and identify the affected pages or rows.
5. Create one candidate row per distinct service/program, not automatically one row per organization or paragraph.
6. Consolidate paired English and Spanish sources before translating. Prefer supplied translations when they accurately describe the same program. Translate missing content faithfully and concisely without claiming that the organization authored the translation.
7. Check current official sources when facts are missing, ambiguous, or possibly outdated. Prefer the organization’s official site, then government or authoritative program pages. Record the supporting URL in `source_url`. Never invent an organization, program, phone, address, schedule, eligibility rule, language, cost, or contact method.
8. When completing existing resources, read [references/research-checklist.md](references/research-checklist.md) and audit the export before researching. Complete only missing or explicitly requested fields. Preserve reviewed values and report conflicts instead of silently replacing them.
9. When auditing existing resources or a large import, run `scripts/audit-resource-titles.mjs`. Review every shared-title group and every title that duplicates the organization. Classify each finding as a legitimate shared service label, a title/content mismatch, an ambiguous title, or a true duplicate; never force cosmetic uniqueness.
10. Deduplicate within the input and against an existing-resource export when available. Match in this order:
   - exact existing slug;
   - normalized organization plus localized title;
   - strong combinations of official website, phone, physical address, and program name.
   Flag uncertain matches instead of merging them.
11. Normalize every row using [references/quality-rules.md](references/quality-rules.md). Read that file before producing the CSV. Classify from source evidence and the official program identity, not from previously generated prose. When several services match, select the most specific service actually represented by the row instead of accepting the first keyword match.
12. Generate UTF-8 CSV with the exact live header order. Quote fields correctly, preserve accents, and use `|` for list values unless the live importer specifies otherwise.
13. Run `scripts/validate-puente-csv.mjs` against the project and output. Fix all importer errors and review every quality warning. Audit every row to confirm that neither localized title equals nor redundantly contains `organization_name`.
14. Audit titles and merged prose editorially. Require each localized title to identify the service or population without relying on the summary for essential context. Rewrite overlapping source fragments into one coherent summary; never concatenate generated sentences mechanically.
15. Rerun both validators after corrections. Document every remaining shared-title group and why it is legitimate, such as separate food pantries, equivalent home-health providers, or distinct service locations. Confirm that no title equals the organization and that no true duplicate was given an artificial title merely to make it look unique.
16. Deliver:
   - `<source-name>-puenteatx-import.csv`;
   - `<source-name>-puenteatx-review.md` only when unresolved issues, assumptions, duplicate candidates, or missing fields exist.

## Existing-resource enrichment

When the user supplies a JSON export of existing resources:

1. Run the gap audit before web research:

```bash
node <skill-dir>/scripts/audit-resource-gaps.mjs \
  --project <puente-project-root> \
  --existing <resources.json> \
  --out <gap-report.csv>
```

2. Use the report to research only empty fields. Do not rewrite populated fields unless the user explicitly requests correction or an authoritative source reveals a material conflict.
3. Preserve each existing `slug`; use it as the update identity.
4. Populate the normal Puente ATX CSV columns. The research checklist is an intermediate quality-control format, not a second import schema.
5. Validate with `--existing` and confirm rows resolve to `update` or `unchanged`, not unintended `create` actions.
6. Recommend **Completar solo campos vacíos** only for a first enrichment that must preserve populated values. Recommend **Actualizar campos incluidos** when a corrected CSV intentionally replaces titles, categories, translations, or other populated fields from an earlier import. Confirm in the preview that the rows resolve to `update` and that the intended fields appear in the change list.
7. Provide a review report for conflicts, unverified facts, ambiguous locations, unsupported Spanish availability, and fields that remain empty.

## Existing-title audit

Run before and after correcting an existing export:

```bash
node <skill-dir>/scripts/audit-resource-titles.mjs \
  --existing <resources.json> \
  --status draft \
  --out <title-audit.csv>
```

The audit is read-only. For each finding:

1. Keep a shared title when it accurately names the same service type at different organizations or locations.
2. Retitle a resource when its title omits essential context or conflicts with its immutable description or official source.
3. When two records represent the same program, select the strongest canonical record, preserve activity and the stable slug, merge verified complementary coverage, and archive the duplicate rather than inventing different titles. Never permanently delete it.
4. Recheck every targeted ID immediately before mutation, compare a fresh export afterward, and require that only approved IDs changed.

### Duplicate detection at scale and the shared-title false positive

Run `node scripts/audit-db-resources.mjs --project <root> --input <export.json> --out-dir <dir>` for a full duplicate and field-quality sweep (see `duplicate-clusters.txt`, `likely-duplicate-pairs.csv`, `field-issues.csv`). Its similarity scoring produces one recurring false-positive shape: dozens of distinct organizations that all cite the same referral hub as `website_url` (for example `centraltexasfoodbank.org/find-food-now`) and share a generic, correctly-repeated title such as `Despensa de alimentos` / `Food pantry`. These cluster together only because the anchor and title text match, not because they are the same resource — exclude any cluster whose only shared anchor is a third-party locator/referral site before reviewing it as a duplicate candidate. The same caution applies to naturally repeated multi-location services (a food bank's several city-specific mobile pantries, a clinic chain's several branches, one organization's genuinely distinct programs such as general primary care versus its separate MAP-eligibility-assistance service) — one row per distinct service or site is correct, not a duplicate, even when title and summary text are nearly identical.

For pairs that share a hard anchor (exact phone, exact normalized address, or exact website domain) and near-identical title/summary text, confirm the duplicate with a **field-by-field diff** across every column (address, city, postal_code, phone, sms_phone, whatsapp_phone, email, website_url, hours_es/en, eligibility_es/en, required_documents_es/en, application_steps_es/en, accessibility_notes_es/en, service_area_es/en, latitude/longitude) before removing anything. When the losing (duplicate) record holds a real, non-boilerplate value that the surviving record lacks — a street address, a distinct hours string, a required-documents list, real coordinates — merge that value into the surviving record first (with a verification note citing the merged-from slug and date), and only then mark the duplicate resolved. Do not merge a named staff member's personal email, an unrelated department's email, a distant headquarters address that does not serve the record's stated area, or generic boilerplate text (e.g. "Contact the organization to confirm availability") — none of that counts as rescuable unique data.

Prefer the record with the more recent `updated_at` as the survivor when both sides are otherwise equivalent in quality; the older one is the one to resolve.

**The address anchor misses spelled-out vs. abbreviated variants unless folded first.** `901 West Braker Lane` and `901 W. Braker Lane` are the same address but normalize to two different strings under a plain lowercase-and-strip-punctuation pass, so the exact-address anchor silently fails to connect them — and because the similarity pass falls back to title/summary text when it can't find two shared anchors, a genuine duplicate can slip through entirely if the titles also happen to differ in wording (a real case: `St. Vincent De Paul - Diocesan Council of Asutin` / "Despensa de alimentos" vs `Society of St. Vincent de Paul Diocesan Council of Austin` / "Despensa de Alimentos St. Vincent de Paul" — same food pantry, same phone, address spelled two ways — found only because a user noticed the two cards on the map by chance, not by the audit). `scripts/audit-db-resources.mjs` now folds common directional words (`west→w`, `north→n`, `south→s`, `east→e`) and street-suffix words (`street→st`, `lane→ln`, `avenue→ave`, `drive→dr`, `road→rd`, `boulevard→blvd`, `highway→hwy`, `court→ct`, `circle→cir`, `place→pl`, `parkway→pkwy`, `trail→trl`, `suite→ste`, `apartment→apt`) before building the address anchor — but treat this as a floor, not a guarantee: a fresh anomaly (a typo, a different abbreviation style, a missing period) can still defeat it, so a same-phone pair with a *visually* matching but not *byte-identical* address is still worth a manual look even when the script doesn't cluster it.

**A cluster sharing one hard anchor (same phone/address) can mix a true duplicate with a legitimately distinct co-located service** — don't clear the whole cluster as "different services, not a duplicate" just because one member clearly is different. The St. Vincent de Paul address above actually had three records on the same phone number: two were the same food pantry (a true duplicate) and the third was that organization's separate SVdP Pharmacy Program (a genuinely distinct service, correctly left alone). Check every pair within a same-anchor cluster individually — same category and near-identical summary content means duplicate; different category or clearly different program scope means legitimate multi-service.

Two cheap, high-precision signals worth checking first on any export, before the similarity pass:
- A `slug` ending in `-2`, `-3`, … that the importer auto-appended on collision. It only does this when it could not match an existing record and created a new one, so the suffixed slug is almost always a true duplicate of the un-suffixed one (`integral-care-integral-care-2` beside `integral-care-integral-care`, `catholic-charities-…-2`, `greater-mt-zion-church-…-2`).
- A record whose Spanish title matches another record's English title under the same normalized organization. The importer's name-plus-title match runs per language, so a listing entered once in Spanish and once in English becomes two separate records — often both `published` (`hope-counseling-program-williamson-county` beside `programa-de-consejeria-hope-…`, `communitycare-primary-and-specialty-health-services` beside `atencion-medica-primaria-y-especializada-…`). Merge the language-split pair into one bilingual record; do not treat the thinner-language side as a distinct service.

A plain `select * from resources` export (Supabase Table Editor or SQL) has three shapes that trip naive parsing: `primary_category_id` is a UUID, not a slug — map it through `categories.js`; additional categories are absent entirely, since they live in the `resource_categories` join table rather than a column; and `languages` / `service_methods` / `keywords_*` come back as JSON arrays (`["es","en"]`) or Postgres array literals (`{es,en}`), not `|`-delimited strings. `scripts/audit-db-resources.mjs` already handles all three — a hand-written query or a different export tool will not.

### Tagging convention when the admin app cannot hard-delete

The `resources` table's `authenticated` role has `SELECT`/`INSERT`/`UPDATE` but **no `DELETE` grant** — attempting a REST `DELETE` returns `42501 permission denied`. This is intentional (never permanently delete; archive instead), and a service-role key must never be introduced to work around it. Practical convention for flagging outcomes so a human admin can act from the dashboard list view without opening each record:
- Set `status = 'archived'` and append a line to `verification_notes` reading exactly `DUPLICADO` (or `DELETE` once a duplicate's rescuable data, if any, has already been merged into the survivor) — always as its own paragraph, appended, never overwriting existing notes.
- For records confirmed safe to remove entirely, also **prepend `DELETE: ` to both `title_es` and `title_en`** — the admin list/table view renders only the localized title (bold) and `organization_name` beneath it, not `verification_notes`, so a note-only tag is invisible without opening the record. The title prefix is what actually surfaces in the dashboard and its search box.
- For an archived record found to have no real conflict and to already satisfy the publish-required fields (see below), append `PUBLISH` to `verification_notes` as a lighter-weight flag, or set `status = 'published'` (with `published_at`) directly once the user has confirmed they want an actual status flip rather than just a text flag.
- True hard deletion requires the user to act directly in the Supabase Table Editor (a database-level operation outside this project's own admin app and outside this skill's reach).

Before any status flip to `published`, verify the record already satisfies the DB's own publish gate (`organization_name`, a title in either language, a summary in either language, `primary_category_id`, at least one of `phone`/`email`/`website_url`, `source_url`, and `last_verified_at` all non-empty) — the `PATCH` is rejected by a check constraint otherwise, and "no conflict with a published duplicate" is not the same thing as "ready to publish."

## Stored-coordinate audit

Use this workflow when auditing resources that have a physical service address but lack valid coordinates. Geocode once during the controlled audit and persist approved coordinates; never geocode on demand when a visitor opens the Resource Finder.

1. Export and preserve a timestamped, immutable backup of all targeted records before proposing or applying changes. Include both published and draft resources unless the user narrows the scope.
2. Select only records with a physical service address that is operationally useful and with either coordinate missing, nonnumeric, zeroed, out of regional bounds, or otherwise invalid. Do not geocode phone/online-only resources or headquarters that are not service locations.
3. Normalize the address for lookup without overwriting its displayed form. Use address line, unit when relevant, city, state, and ZIP code. Flag incomplete or internally conflicting addresses before lookup.
4. Use an approved geocoding source to obtain candidate latitude and longitude once. Record the original address, normalized query, provider, lookup date, returned formatted address, coordinates, match type or precision, confidence evidence, and any discrepancy in an audit report.
5. Classify every candidate:
   - **Exact/high confidence:** rooftop, parcel, or verified establishment match whose returned street number, street, city, state, and ZIP are consistent. Eligible for a proposed batch update.
   - **Approximate/ambiguous:** interpolated street, multiple candidates, partial match, conflicting city/ZIP, entrance ambiguity, or materially displaced point. Require human review before update.
   - **Unresolved:** incomplete address, no result, locality/ZIP centroid only, or result outside the expected service region. Do not invent or save coordinates.
6. Give every approximate, ambiguous, tied, or initially unmatched physical address a second review before rejecting it:
   - Check the current official program or organization page first; use an authoritative government or institutional directory only when the official page is unavailable. Record the verification URL and access date.
   - Treat harmless standardization—such as `Highway` versus `US HWY`, suffix abbreviations, punctuation, unit omission, or the recognized local spelling of `Manchaca`—as acceptable only when street number, street identity, municipality, and ZIP resolve to the same physical site.
   - Accept a non-exact geocoder result only when the online source confirms the service location and the returned point has one unambiguous candidate within the expected region. Record why the discrepancy is harmless and retain the geocoder's match type; do not relabel it as exact.
   - Reject or escalate directional changes (`E` versus `W`, `N` versus `S`), different street numbers, conflicting municipalities or ZIPs, multiple candidates, closed or moved locations, and headquarters that are not service sites. If the official source proves the stored address is wrong, propose the address correction separately from the coordinate update.
   - For an intersection, accept a `StreetInt` point only when the resource actually represents a stop, route, outreach point, or service delivered at that intersection and the official source confirms it. Never use an intersection as a substitute for a missing building address.
   - Continue researching plausible street addresses that one provider cannot match with another approved source whose terms allow storing the result. Document provider, precision, confidence, attribution requirements, and cross-source agreement. Never copy map coordinates from an ordinary search-result snippet or URL.
   - Keep variable, confidential, multi-site, or insufficient addresses unlocated until a specific public service location is confirmed. Do not select the “most likely” branch or use a centroid merely to maximize marker coverage.
7. Never use a city, county, or ZIP centroid as the resource marker. ZIP centroids may center a user's search, but they do not establish a service location.
8. Before any production mutation, present the report and obtain explicit user approval. Re-export and recheck each targeted ID immediately before mutation so stale data or concurrent edits cannot be overwritten.
9. Update only `latitude` and `longitude` for approved matches unless the user separately approves an address correction. Also set the documented geocoding status and timestamp. Preserve IDs, slugs, publication status, reviewed content, and all unrelated fields.
10. Export the records again after mutation and compare by ID. Require exact agreement with the approved operation set, no unexpected changed IDs or fields, valid regional bounds, and idempotency on a second dry run.
11. Verify representative ZIP searches in the Resource Finder. Confirm approved published resources appear as markers at the expected establishment, while drafts remain absent from public results until published. Report resources that remain unlocated separately.

Required deliverables are the pre-change backup, a coordinate-candidate report with confidence classifications, the explicitly approved operation set, and a post-change comparison. Keep production unchanged when the request is only to audit, prepare, explain, or update this skill.

### Geocoding source specifics and address-currency checks

The US Census Bureau's public geocoder (`https://geocoding.geo.census.gov/geocoder/locations/onelineaddress?address=<addr>&benchmark=Public_AR_Current&format=json`, no key required) is the default first choice: a single match (`addressMatches.length === 1`) with matching street number/city/ZIP is exact/high confidence; zero or multiple matches need the fallback below. Two Census quirks are not, by themselves, reasons to reject a match: it sometimes returns a different directional prefix than the one stored (`E` vs `W` Stassney Ln, `E` vs `W` Carrie Manor St in one audit) while the returned coordinate is still correct for the real building — verify the *stored* address against an independent official source before deciding which directional is right, don't just trust whichever one Census echoes back; and it sometimes normalizes to a different ZIP than the one on file (5325 Airport Blvd normalized 78753→78751) — when independent sources confirm the normalized ZIP, that is itself a real data error worth correcting, not a mismatch that disqualifies the geocode. When Census returns no match (common for suite/highway/building-name addresses), fall back to a live map search and read the coordinate out of the resulting place URL's `@lat,lon,zoom` or `!3d<lat>!4d<lon>` segment — but only after confirming there is an actual current business/site at that address, not a bare parcel.

Before trusting any stored address, check whether the organization has simply moved. Cross-reference against a current, official locator (the organization's own "locations" page, or the authoritative directory the record's `source_url` already cites, e.g. Central Texas Food Bank's Find Food Now) rather than assuming a stored address is still valid just because it was valid when first entered — the source-cited directory can itself have moved on since the record was created (an audit this project ran found a women's-health clinic still listed at a location the organization's own site said it had vacated a year earlier, and a food-pantry record whose address no longer appears anywhere in the food bank's current partner list at all). If the org moved, treat the address correction as its own approved edit, separate from the coordinate refresh, and cite the org's own current page as the source.

**Do not attribute a co-located host's phone number or address to a program merely operating out of that host's building** (a school hosting a monthly mobile food distribution, a housing authority building that also contains an unrelated resident council, a church basement hosting a walk-in program run by a different sponsoring organization) unless an official source explicitly ties that phone/address to the program itself, not just the building. When no such source exists, leave the field blank rather than guess by proximity.

### Address-field hygiene: one street per line, city/state/ZIP in their own columns

`address_line_1` holds exactly one street address. `address_line_2` holds **only** a unit designator (`Ste 200`, `Bldg C`, `Apt 4`, `#210`, `Room 5`, `Floor 2`) — never a second street address, a descriptive label, or prose. The card renders `[address_line_1, address_line_2, city, state, postal_code].filter(Boolean).join(', ')` and builds its Google Maps link from that same join, so anything extra in a street line is displayed twice and corrupts the map query. Two real shapes found in this DB:

- **A whole second building crammed into `address_line_2`** — `"Programs & Services: 2001 Railroad Avenue"` (The Caring Place operates the pantry at 2000 and financial assistance at 2001). Fix: clear `address_line_2`; move the second location into `description_*` prose and mention it in the `hours_*` / summary schedule if the hours differ by building. Do not split into two resources unless the two services are genuinely distinct programs.
- **The full `"street, City, TX ZIP"` string in `address_line_1`** while `city` / `state` / `postal_code` columns are also populated (14 records in one sweep) — renders as `"301 Lee St. Smithville, TX 78957, Smithville, TX, 78957"`. Fix: cut `address_line_1` back to just the street (`"301 Lee St."`); backfill `city` from the stripped text where that column was empty; leave `postal_code` alone (it was already correct).

`scripts/audit-db-resources.mjs` now flags these: `address_line_2_is_a_street_address`, `address_line_2_has_label`, `address_line_2_prose_not_unit`, `address_line_1_multiple_addresses`, `address_line_1_has_city_state_zip`, and `address_line_{1,2}_has_{phone,email,url}`. A bare 5-digit street number (`12012 Park Thirty Five Cir`) is **not** a ZIP — the check only fires on an embedded state name or a ZIP that trails a `TX`/`Texas` token. Any `address_line_1` / `address_line_2` edit fires the geocode-reset trigger (see the live-DB section below), so preserve coordinates with the documented two-`PATCH` sequence: address fix first, then a coordinates-only `PATCH` restoring the record's existing `latitude`/`longitude`/`geocode_status`/`geocoded_at` unchanged — this cleanup is cosmetic on the address text and must not move or drop a single pin.

### `hours_*` fields sometimes already contain phone numbers or URLs

Some existing records' `hours_es`/`hours_en` values are not a clean schedule string — they mix in a phone number and/or a bare-domain URL as part of the same free-text paragraph (e.g. `"Teléfono: (512) 469-9020 (martes)... | Horario: martes y jueves..."`). Before copying an hours value into `summary_es`/`summary_en` (a common admin request), scan it for a phone pattern or a domain pattern (`\b(?:[a-z0-9-]+\.)+(?:com|org|net|gov|edu|us|io)\b`, not just `https?://`/`www.` — bare domains like `YourTexasBenefits.com` or `ReadyCentralTexas.org` will otherwise slip past a narrower regex) and, if found, exclude that hours value from the copy rather than reproducing contact info inside the public-facing summary (see the "free of phone numbers, emails, URLs" rule below). If a summary already contains an appended `Horario: <text>.` / `Hours: <text>.` clause built this way, it can be reverted precisely by re-deriving that exact suffix from the still-present `hours_*` value and stripping it back off — because the append is a known, reproducible template, this is safe to automate and does not require guessing what the original summary said.

## Live-database access via an authenticated admin session (no service-role key)

For a direct, live audit or correction against production (as opposed to preparing an offline import CSV), the sanctioned path is the same one `scripts/*-via-cdp.mjs` in this repo already use: a Chrome window opened with `--remote-debugging-port=<port> --user-data-dir=<persistent-profile-dir> https://puenteatx.org/admin`, logged in **by the user themselves** (never enter their credentials). Once logged in, a Node script connects over Chrome DevTools Protocol, reads the session token the app already stores in `sessionStorage` under `puente-atx:admin-session`, and issues plain `fetch()` calls to the Supabase REST API (`apikey: <anon key>`, `Authorization: Bearer <access_token>`) from inside that authenticated page context — this never touches a service-role key and stays within the same RLS/permission boundary as a human admin clicking through the UI.

Operational notes learned running this pattern repeatedly in one long session:
- The public `VITE_SUPABASE_URL` and anon key (a `sb_publishable_...` string in newer Supabase projects, not necessarily a JWT) can be read straight out of the site's own already-shipped JS bundle if `.env.local` isn't available locally — they are meant to be public/browser-exposed, so this is not a secret extraction.
- A script invoked as `node --input-type=module -` (piped from a scratchpad file via stdin) still resolves bare imports like `ws` from the **current working directory's** `node_modules` — running it with `cwd` set to the project root lets a script that physically lives outside the repo (e.g. in a scratchpad) still `import` the project's installed dependencies, without ever writing a file into the git working tree. This matters because another session or the user's own tooling may be working in the same repo directory concurrently; scratch files left inside the repo have been picked up and committed by an unrelated `git add -A` from a different process mid-session.
- The Chrome window and its authenticated tab can close or crash without warning (observed twice in one session) — a script suddenly getting "no admin tab found" or `ECONNREFUSED` on the debugging port means the window is gone, not that the code is wrong. Recover by opening a **new** tab/window in the *same* profile directory (`Target.createTarget` against the browser-level `webSocketDebuggerUrl`, or relaunching Chrome with the same `--user-data-dir` and port) and asking the user to log in again — `sessionStorage` does not survive a closed tab, so the token is genuinely gone, not just stale.
- Any `UPDATE` that touches `address_line_1`, `address_line_2`, `city`, `state`, or `postal_code` fires a database trigger (`resources_reset_geocode_on_address_change`, see `supabase/migrations/009_resource_geocoding_status.sql`) that **wipes `latitude`/`longitude` back to null and `geocode_status` to `pending`** unless the *same* `UPDATE` also supplies new, non-null, changed `latitude`/`longitude` values. Fixing only a ZIP code, for instance, silently discards previously-approved coordinates; always geocode-and-address-fix in one combined `PATCH`, or immediately follow up with a coordinates-only `PATCH` (which does not trigger the reset, since no address column is included) if the fix genuinely has to happen in two steps.
  - **The trigger checks `IS DISTINCT FROM`, not merely "is a value present."** Re-sending the record's own current, unchanged `latitude`/`longitude` in the same `PATCH` as an address-only field fix (postal_code, a typo fix, a merge) does **not** count as supplying new coordinates — the trigger sees no change on those two columns and wipes them anyway, exactly as if they'd been omitted (hit live 2026-09-08 patching only `postal_code` on an otherwise-geocoded record: `latitude`/`longitude` came back `null` immediately after, despite being included in the request body with their existing values). If the coordinates genuinely aren't changing, do the address fix and the coordinate restore as two separate `PATCH` calls — the second one touching only `latitude`/`longitude`/`geocode_status`/`geocoded_at` and no address column, which the trigger's outer `IS DISTINCT FROM (old address row)` check then skips entirely. Re-verify with a fresh export after, the same as any other coordinate mutation.
- Before writing anything, export and locally save a fresh full JSON snapshot of every targeted row (not just the ones already suspected of needing a change) — concurrent edits from the user or another session are a real, observed risk in this project, not a hypothetical one, and a snapshot taken minutes earlier can already be stale by the time a write actually lands.

## Output standards

- Produce drafts ready for admin review; never publish or import automatically.
- Populate both Spanish and English titles and summaries.
- Write `title_es` and `title_en` as concise service or program names only. Keep the institution in `organization_name`; never append or prepend it to a title merely for identification because the Puente ATX interface displays the organization separately. Examples: use `Asistencia legal` with organization `Texas Rio Grande Legal Aid`, and `Atención veterinaria` with organization `Emancipet`.
- Make every title specific and self-contained enough to distinguish the service. Include the essential subject or population when omitting it would make the title ambiguous. For example, use `Apoyo para sobrevivientes de violencia y agresión sexual` / `Support for survivors of violence and sexual assault`, not `Apoyo para sobrevivientes` / `Survivor support` when the verified source provides that context.
- Do not make titles unique merely by appending the organization, county, or arbitrary wording. Repetition is valid when the title accurately describes equivalent services; distinguish locations through organization and location fields already displayed by Puente ATX.
- Prefer a specific supported service over a broad incidental keyword. In particular, distinguish veterinary care from human dental care, legal assistance from housing topics mentioned in a legal description, Lifeline phone service from household or family language, adult education from employment language, and survivor support from housing that is part of a violence-response program.
